一、项目概述

MultiBilling 是面向团队/小组/家庭的多人共享记账工具。实验一整理出 17 条需求（REQ-001~017），核心问题：协作授权、审核流转、变更留痕、桌面移动适配。

技术选型

层次选型理由
前端Vue 3 + TypeScript + Vite组合式 API 模块拆分；TS 编译期校验枚举。
接入层NginxHTTPS、静态资源、反向代理。
应用层Spring Boot 3 / Java 17事务、校验生态成熟。
数据库MySQL 8.0强一致；JSON 存快照与配置。
缓存/锁Redis 7会话、每账本写锁。
对象存储MinIO（S3 兼容）附件分离存储，预签名下载。
部署Docker Compose五容器一键拉起。

三、软件架构设计

3.1 分层架构

层次组成职责
表现层Vue 3 SPA渲染、表单校验；权限隐藏仅作体验层。
接入层NginxHTTPS、静态资源、/api/** 反向代理。
接口层REST ControllerDTO 校验、上下文解析；无业务分支。
应用层应用服务用例编排、事务、领域事件。
领域层实体、策略状态迁移、重复判定、金额限制、投票、权限。
基础设施层仓储、MinIO、Redis、MySQL持久化、存储、缓存。

3.2 模块交互

  • 写路径单向：Controller → Service → Domain → Repository。
  • 存档旁路：领域事件驱动，业务与存档同事务。
  • 统计只读：固定 status='APPROVED'。

3.3 部署结构

单机 Docker：Nginx(443/80) → Spring Boot(8080) → MySQL(3306) / Redis(6379) / MinIO(9000)。外部仅 Nginx 暴露端口。

3.5 关键设计决策

#决策内容理由
D1身份与权限分离MemberIdentity{OWNER,PARTICIPANT} + MemberRole{ADMIN,MEMBER}避免角色组合爆炸
D2四分区=状态投影单一 EntryStatus，板块由状态过滤历史连续、外键稳定
D3状态迁移集中EntryWorkflow 统一执行，非法抛异常避免分散 if 漏洞
D4乐观锁并发entry.version 递增，冲突 409记账并发低，乐观锁更轻
D5作废票数快照创建时快照管理员数；agree×2 > snapshot避免中途人数变化导致不可解释
D6修改不改旧条目原条目 INVALID，新条目 PENDING 重审保留完整历史
D7存档旁路化领域事件驱动，同事务提交新增动作无需改存档代码
D8统计单一出口仓储层固定 status='APPROVED'防止报表遗漏条件

六、大模型辅助设计过程记录

使用场景生成结果优缺点修改优化
领域模型与类图初稿：将 REQ-001~017 交给大模型识别实体、属性、关系9 个类，基数基本正确；但身份权限合并为一个枚举，用三布尔字段表示板块，缺少修改申请/作废实体优：速度快、结构完整。缺：对字段语义不敏感，倾向名词变类拆分 MemberIdentity/MemberRole；布尔合并为 EntryStatus；新增 5 个实体；Statistics 降级为服务
作废投票边界推演：请大模型列出 REQ-010 的边界情况7 条边界，覆盖良好；但判定式 agree/admin≥0.5 语义错误，建议实时查人数优：清单能力强。缺：自然语言转数学符号易错，倾向最省事实现快照管理员总数；agree×2>snapshot（严格多数）；唯一索引保证一人一票；72h 超时
UI 布局生成：按设计规范生成 12 个界面 HTML/CSS视觉整齐；但 SVG 无 viewBox 撑破卡片、侧栏文字竖排、移动端固定栏遮挡优：一致性好、批量快。缺：看不见渲染结果，CSS 失效需实际渲染发现Puppeteer 量化测量溢出像素；逐项修复后 12 屏全部通过
需求覆盖自查：逐条判断 17 条需求覆盖情况指出 3 处遗漏（REQ-012/005/016）；但把「提到过」等同「已实现」优：不漏行。缺：无法区分写到与落地，结论仅作待核清单逐条人工复核并补充设计

总结。大模型擅长生成结构化初稿、边界清单、批量一致代码、对照检查；不擅长价值判断、语义精确、需看见结果的验收、确认已实现。有效用法是嵌入可验证循环：生成→客观验证→反馈修正。

九、总结

本次实验将 17 条需求推进到可实现粒度：10 模块、9 张 UML 图、11 张表、12 个界面，覆盖全部需求。

  • UML 的价值在于迫使回答「为什么」——身份权限是否拆分、四板块是否建四张表、已审核能否直接回未审核，这些在需求中无答案，必须自定规则。
  • 规则集中比完整更重要。状态/权限/金额/重复/投票/统计口径收敛到少数策略类后，新增规则只改一处，测试逐条覆盖。
  • 界面是规则的一部分。统计口径写在标题下、提交后果写在按钮旁、还需几票画成进度条——把后端约束翻译成用户可感知的信息。

不足：未绘制包图与 ER 图；界面仅静态验证；若干规则基于假设；设计未经过实现检验。
